La redirection de page est souvent utilisée dans le développement pour résoudre des cas spécifiques de traitement. Dans un script PHP, effectuer une redirection consiste à demander au navigateur d'appeler un autre script (ou une autre page).

    Exemple

    On se place dans le cas d'un script login.php qui, lorsqu'il est appelé une première fois via une requête HTTP GET, renvoie le code HTML d'un formulaire de connexion.

    La figure suivante représente ce que l'on souhaite réaliser lors de la soumission du formulaire.

    Lorsque l'utilisateur clique sur le bouton connexion, le script login.php est rappelé (on est dans le cas d'une auto-soumission) :

    • si l'authentication échoue, le script login.php renvoie au navigateur le code HTML du formulaire, accompagné d'un message d'erreur comme 'Echec de l'authentication';
    • sinon, le script login.php envoie une demande de redirection vers le script/page accueil.php.

    PHP fournit la fonction header() pour générer des en-têtes HTTP et les envoyer au client. L'en-tête qui gére les redirections s'appelle Location et doit avoir comme valeur l'URL de la page sur laquelle on redirige le navigateur. Par exemple :
    Location: test_divers/accueil.html
    va rediriger le navigateur sur la page accueil.html située dans le répertoire test_divers.

    • On peut utiliser la fonction header() pour envoyer n'importe quel en-tête HTTP au client.
    • Quand on l'utilise pour envoyer un en-tête HTTP Location, header(), en plus d'envoyer l'en-tête HTTP, envoie au navigateur un code de statut de réponse 302 Found.
      Dit autrement, l'appel dans un script PHP de
      header('Location: page.php');
      entrâine l'envoi au navigateur d'une réponse HTTP ayant le code de statut 302 Found accompagné d'un en-tête Location: page.php.

    On reprend notre exemple : si l'utilisateur envoie un login et un mot de passe valides, la soumission du formulaire de connexion entrâine l'échange des messages HTTP suivants :

    • 1 : le client appelle le script login.php : envoi au serveur d'une requête HTTP POST si le formulaire est soumis avec la méthode POST;
    • 2 : le serveur (compte tenu de l'exécution de l'instruction
      header('Location: accueil.php');)
      envoie au client une réponse ayant le code de statut 302 Found accompagné de l'en-tête HTTP Location: accueil.php
    • 3 : le client envoie une requête HTTP GET pour demander la page accueil.php
    • 4 : le serveur envoie une réponse HTTP avec le code de statut 200 OK contenant, dans le corps du message, le code HTML de la page d'accueil (à condition que le script accueil.php ne réalise pas une nouvelle demande de redirection).

    Notez que l'appel de la fonction header() dans le cas spécifique d'une redirection DOIT être suivi immédiatement de l'arrêt du script avec exit. Si ce n'est pas le cas, le suite du script s'exécutera normalement, avec par exemple toutes les mises à jour éventuelles de la base de données.

    Il est particulièrement important de comprendre que l'exécution de l'instruction header('Location: accueil.php'); n'arrête pas le script, mais envoie "simplement" un en-tête HTTP, tout en fixant le code de statut de la réponse.

    Problème de messages HTTP mal formés

    Suivant la façon dont est configuré PHP, le script suivant peut ne pas s'exécuter correctement et provoquer l'erreur Cannot modify header information - headers already sent.

    Exemple : des sorties avant l'appel de header()

    L'affichage éventuel de ce message d'erreur vient de la façon dont sont construits les messages HTTP : les en-têtes doivent se trouver au début du message et pas dans le corps du message, constitué des sorties d'affichage (i.e. echo ou print) que fait le script.

    Pour éviter ce problème, il y a 3 solutions :

    • configurer PHP avec l'option output_buffering à ON (ou à une valeur supérieure à la taille des sorties générées avant l'envoie de l'en-tête HTTP). Souvent impossible car on n'a pas accès à la configuration du serveur.
    • avoir une grande rigueur et toujours envoyer les en-têtes avant quelque autre sortie que ce soit. Trop hasardeux : le développeur n'est pas toujours strict, le développement ne peut pas toujours être adapté.
    • utiliser les fonctions de buffering comme nous allons le voir dans les pages suivantes.
