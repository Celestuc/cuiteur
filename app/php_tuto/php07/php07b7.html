Nous avons déjà parlé dans le chapitre sur les chaînes de caractères de la "protection des chaînes" quand elles doivent être affichées par le navigateur.

Quand nous affichons des chaînes littérales que nous avons nous-même inclus dans notre code (message d'erreur, label de champ de formulaire, texte explicatif, etc), nous somme sûrs qu'elles ne contiennent pas de code HTML ou JavaScript que nous ne voudrions pas voir exécuter par le navigateur quand il va faire l'affichage de ces chaînes.

Il n'en va pas de même quand nous affichons des chaînes dont nous ne maîtrisons pas totalement la provenance ou la composition. C'est particulièrement vrai pour ce qui est stocké dans une base de données, d'autant plus que la philosophie du "Web 2.0" est une participation accrue des utilisateurs qui sont sollicités pour laisser des messages, des avis, des commentaires, etc.

Rien n'empêche ces utilisateurs s'ils ont des connaissances en HTML ou JavaScript d'inclure des tags ou des instructions dans les textes qu'ils laissent sur tel ou tel site. Si rien n'est fait pour surveiller et inhiber ces éléments de langage, ils seront tout simplement "exécutés" par le navigateur, ce qui peut conduire à des failles de sécurité dans notre site, ou à ce que d'autres utilisateurs soient piégés.

L'exemple suivant illustre du code malicieux saisi dans du texte et stocké dans la base de données.

Exemple : texte avec du code interprété à l'affichage

Le responsable de cette "redirection" vers un site pirate imitant la page de login de Moodle est simplement le morceau de code suivant glissé dans le résumé du livre :
<script>location = "../exemple/login.html"</script>

Pour éviter que du code soit interprété par le navigateur sans que nous le voulions, il faut protéger toutes les chaînes de caractères qui viennent de la base de données avant d'en faire l'affichage. Pour cela, nous pouvons utiliser 2 fonctions :

  • htmlspecialchars() qui renvoie une chaine où seuls les caractères de la syntaxe HTML de la chaine d'origine sont remplacés par leur entité HTML,
  • htmlentities() qui est identique à la fonction htmlspecialchars(), sauf que tous les caractères qui ont des équivalents en entités HTML sont effectivement traduits, notamment les caractères accentués.
Exemple : texte protégé avec htmlentities()

On voit que maintenant le code HTML et JavaScript inclus dans le texte du résumé n'est plus exécuté, mais affiché tel qu'il a été saisi puisque htmlentities() a notamment transformé les < et > syntaxiques du langage HTML en ... entités HTML, c'est à dire en simples &lt; et &gt;. Ainsi, le navigateur ne reçoit plus la chaîne '<script>' (qui signifie pour lui balise ouvrante d'un élément SCRIPT) mais la chaîne '&lt;script&gt;' et il affiche simplement cette chaîne en remplaçant les entités HTML par les caractères correspondant (l'entité &lt; est par exemple "rendu" comme un simple caractère "inférieur".

Je vous invite à regarder le code source de la page obtenue lors de l'exécution du script précédent, vous y retouverez notamment la chaîne '&lt;script&gt;'.

On privilégiera htmlentities() pour protéger les chaînes avant affichage, car elle remplace par leur entité HTML tous les caractères qui ont une entité HTML équivalente.

Le recours à une fonction pour notamment protéger toutes les chaînes d'un tableau est intéressant car protéger toutes les chaines d'un tableau, en les protégeant une par une, peut s'avérer pénible du fait de la répétition du code et des oublis qui peuvent arriver.

La fonction suivante est ajoutée dans notre bibliothéque bib_fonctions.php : 

//__________________________________________________________
/**
 * Protection des sorties (chaînes d'un tableau)
 *
 * La fonction renvoie un tableau où toutes les chaines qu'il
 * contient suivant sa première dimension sont protégées, les
 * autres données du tableau ne sont pas modifiées.
 *
 * @param  array  $tab  tableau contenant des chaines à protéger
 *
 * @return array		tableau avec les chaînes protégées
 */
function tabProtegerSorties(array $tab): array {
	foreach ($tab as &$val) {
		if (is_string($val)){
			$val = htmlentities($val, ENT_QUOTES, 'UTF-8');
		}
	}
	unset ($val); // à ne pas oublier (de façon générale)
	return $tab;
}

Remarques :

  • le tableau est transmis à la fonction par valeur, elle travaille donc sur une copie, et elle renvoie cette copie après avoir protéger les chaînes qu'il contient.
  • Dans la boucle foreach, $val reçoit une référence sur la valeur de l'élément "parcouru" afin que l'on puisse modifier cette valeur en utilisant $val.
    On aurait aussi pû aussi écrire cette boucle comme indiqué ci-dessous : 
    foreach ($tab as $cle => $val) {
	if (is_string($val)){
		$tab[$cle] = htmlentities($val, ENT_QUOTES,
		                                encoding:'UTF-8');
	}
}
    Mais, avec cette deuxième solution, la boucle foreach réalise une copie du tableau (relisez le chapitre consacré aux 'Boucles avec foreach' si nécessaire). Donc la première solution permet d'économiser de la mémoire.
  • Ici, il n'est pas nécessaire de faire un unset($val) à la fin de fonction car justement la variable $val est automatiquement détruite lorsque la fonction se termine.
Exemple : affichage avec notre fonction de protection

Remarques :

  • les fonctions htmlentities() et htmlspecialchars() permettent de convertir les quotes simples ou doubles, contenues dans les chaines de caractères, en entités HTML, ce qui est utile pour placer de telles chaines dans la valeur d'un attribut démilitée par des quotes (dans l'attribut value d'un élément input par exemple);
  • la protection de sorties doit être réalisée au dernier moment, c'est à dire juste avant l'envoi de la chaine de caractères au navigateur. Pour ne pas être faussés, les traitements doivent porter sur des chaines pas encore protégées, et donc ne contenant pas d'entités HTML. (Exemple : le calcul de la longueur d'une chaîne après protection avec htmlentities() est faussé si la chaîne contient des caractères accentués.)
